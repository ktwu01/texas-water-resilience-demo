# From Floods to Droughts: AI-Enabled End-to-End Water Resilience for Texas

A runnable demonstration of the analysis chain described in the proposal
**"From Floods to Droughts: AI-Enabled End-to-End Water Resilience for Texas"**
(25-WATER25_2-0155, PI Zong-Liang Yang, The University of Texas at Austin).

It answers one question at three scales: **when can a high-magnitude flow be
responsibly captured and recharged, and what is stopping you?**

> ### This is a demo. The data is synthetic.
>
> There are no observations in this repository. Every value is generated by a
> stochastic simulator in `src/twr/synth.py`. Nothing here is an observation, a
> forecast, or a finding about Texas hydrology. The Texas Water Development
> Board, the Rolling Plains Groundwater Conservation District, the City of
> Kerrville, and NASA have not reviewed, endorsed, or supplied anything in it.
> Every infrastructure capacity is an invented placeholder marked
> `provenance: illustrative`.
>
> Read [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md) before quoting any number.

## Quick start

```bash
git clone <this repo> && cd texas-water-resilience-demo
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"

python scripts/run_pipeline.py --fast        # ~15 s, small ensemble, no cross-validation
python scripts/make_report.py                # static HTML briefing
open outputs/report.html
```

The full run, including leave-one-basin-out cross-validation over seven basins:

```bash
python scripts/run_pipeline.py --scenario     # ~2.5 min on a laptop, no GPU
python scripts/make_report.py
```

Optional interactive dashboard:

```bash
pip install streamlit
streamlit run dashboard/app.py
```

`make demo` does the fast path end to end. `make test` runs the test suite in
about 20 seconds.

Both views open on a map of Texas showing where in the state high-magnitude flow
is capturable this week: marker colour is the operational flag, marker area is
expected capturable volume. The state outline is a real US Census cartographic
boundary; the markers are approximate placeholder locations, not gauge
coordinates. See [`docs/DATA_SOURCES.md`](docs/DATA_SOURCES.md#geography).

To publish either view for free, see [`docs/DEPLOY.md`](docs/DEPLOY.md):
GitHub Pages for the static briefing, Streamlit Community Cloud for the
dashboard. `make site` builds locally exactly what Pages publishes.

Everything is deterministic: same seed, same numbers, on any machine.

## What it computes

### The Capture Index

```
CI = P( feasible capturable volume >= the site's operational threshold )
```

Every member of a bootstrap ensemble is pushed through the full constraint chain,
and the index is the fraction that survive above the threshold. So it is a
probability that **an action is worth taking**, not a probability of rain. A
basin can be about to flood and score zero because the aquifer is full or the
water is fully appropriated.

### The flag system

| Flag | Capture Index | What it means |
| --- | --- | --- |
| `NO_ACTION` | < 0.20 | no opportunity in the window; routine monitoring |
| `WATCH` | 0.20 - 0.45 | possible; confirm headroom, watch gauges daily |
| `STANDBY` | 0.45 - 0.70 | likely; pre-position pumps, confirm permit status |
| `CAPTURE` | >= 0.70 | execute diversion and recharge within the window |
| `BLOCKED` | low, but water present | a hard limit is in the way; see the binding constraint |

`BLOCKED` is separated from `NO_ACTION` deliberately. "There is no water" and
"there is water you cannot legally or physically take" are different messages and
lead to different work.

### The binding constraint

Every assessment names the limit that is actually in the way, because that is
what determines who a manager calls:

`eflow_pulse` (the river needs it) · `water_rights` (call TCEQ) ·
`annual_permit` (permit amendment) · `diversion_rate` / `conveyance` /
`treatment` (capital project) · `recharge_capacity` (drill or rehabilitate wells) ·
`storage_headroom` (recover before recharging) · `hydrologic_availability` (the
river is simply low)

In the shipped configuration, across every day flagged `STANDBY` or `CAPTURE`,
the limit that would bind if the opportunity materialised is `recharge_capacity`
21 times, `annual_permit` 11 times, and `water_rights` 6 times. Well-field
injection capacity, not water availability, is the most common limit on turning a
synthetic Texas flood into drought storage. Whether that holds for real Texas
utilities is exactly the question this structure exists to ask.

### Three nested scales

| Scale | Decision unit | Question |
| --- | --- | --- |
| State | TWDB screening | where in Texas is HMF capturable this week? |
| Watershed | Rolling Plains GCD | is this a MAR opportunity, and how large? |
| Facility | City of Kerrville ASR | do we mobilise, and what would change the answer? |

The same forecast yields different indices at each scale, because each has its own
threshold and its own hardware.

## Layout

```
config/            basin and site definitions (all placeholders)
src/twr/
  units.py         exact unit conversions, the only place a factor of 1000 can hide
  synth.py         conceptual hydrology -> sensor-like variables
  ingest.py        loader interface + registry of the real NASA/USGS products
  features.py      causal features, forward-looking targets, leakage discipline
  hmf.py           high-magnitude flow thresholds, excess volume, event catalogue
  aquifer.py       lumped storage and recovery accounting
  constraints.py   mass balance, environmental flow, water rights, hardware
  model.py         two boosted heads, bootstrap ensemble, OOB residual sampling
  uncertainty.py   leave-one-basin-out spatial CV, interval coverage
  capture_index.py the index, the flag ladder, the action text
  pipeline.py      end-to-end orchestration across the three scales
  scenarios.py     facility-scale what-if: hold the forecast, vary the hardware
  geo.py           the map layer: vendored Texas outline, approximate site points
scripts/           run_pipeline, make_report, build_site, make_synthetic_data, evaluate_downscaling
dashboard/app.py   Streamlit prototype
data/geo/          the one real dataset: US Census Texas boundary, public domain
docs/              ARCHITECTURE, DATA_SOURCES, DEPLOY, LIMITATIONS, ROADMAP
tests/             138 tests, including leakage, monotonicity, and regression guards
```

On the shipped synthetic data, leave-one-basin-out cross-validation gives event
AUC 0.66-0.88 and observed coverage of the nominal 80% interval of 0.86-0.94
across the seven folds. The learned downscaling step beats bilinear interpolation
by 15.4% RMSE. Those are properties of the simulator, not of Texas.

## Design decisions worth knowing

**Spatial cross-validation, never random k-fold.** Adjacent days in a daily
hydrologic record are near-duplicates, so a random split reports skill that
evaporates on a new basin. Every fold holds out an entire basin.

**Uncertainty has two terms.** Bootstrap spread alone gave nominal 80% intervals
that covered about 4% of observations, because the ensemble members agree closely
on a target that is zero most days. Adding out-of-bag residuals binned by
predicted magnitude brings observed coverage to 0.86-0.94. Binning matters: the
scatter is strongly heteroscedastic, and a pooled residual manufactures phantom
floods on dry days.

**Two binding-constraint fields, not one.** `binding_constraint` is what limits
the planning case and is what makes a row `BLOCKED` rather than `NO_ACTION`.
`binding_if_captured` is what would limit the response if the opportunity does
materialise. Collapsing them either way produces nonsense: using the
unconditional median alone yields dashboard rows reading "WATCH, binding: no_hmf",
and using the conditional median alone labelled 1701 of 2555 statewide days
`BLOCKED` because a legal limit binds the flood case almost every day.

**Mass balance bounds the learner.** Fitted in log space and sampled through an
exponential, the model emitted 1.3e8 AF of excess in a 7-day window on the Brazos,
two orders of magnitude past its own training data. Predicted volume is now capped
by the antecedent rainfall the catchment actually received, and the share of
samples clipped is reported rather than hidden.

**Excess volume is reported as a median, never a mean.** The predictive
distribution is heavy tailed, so its mean is dominated by a few extreme draws and
is not a number to plan against.

**Configuration that cannot work is rejected at startup.** Two sites originally
had operational thresholds their own well fields could not deliver within the
forecast window, pinning the Capture Index at zero forever, which looks exactly
like a hydrologic finding. `pipeline.validate_site_feasibility()` now refuses to
run such a configuration.

**Reproducibility is tested across processes, not within one.** Per-basin RNG
seeds are derived with CRC32, not the builtin `hash()`, which is salted per
interpreter by `PYTHONHASHSEED`. Seeding from `hash()` made the synthetic record
different on every run while an in-process reproducibility test passed happily.
The test suite now checks determinism in subprocesses under three different salts,
and isolates the on-disk record cache so results cannot depend on what a previous
run left behind.

**No fabricated identifiers.** Gauge IDs are `SYN-*` and `usgs_site_no` is `null`
throughout, because a plausible-looking fake USGS site number is worse than a
blank: a blank cannot be mistaken for a citation. A test enforces this.

## Where the real work is

[`docs/ROADMAP.md`](docs/ROADMAP.md) has the detail. The short version: real
observations behind `ingest.load_observed()` are a scoped engineering task,
numerical weather prediction inputs are the largest available skill gain, and the
ARL 6 claim in the proposal is earned by co-production with operators rather than
by code. Flag thresholds and operational thresholds are placeholders that only a
utility can set, because their real values encode the cost of mobilising a crew
against the cost of missing a flood.

## Requirements

Python 3.10+, numpy, pandas, scikit-learn, PyYAML, matplotlib. Streamlit is
optional; `scripts/make_report.py` renders the same content without it. No GPU
and no PyTorch: the super-resolution step uses a ridge regression on patch
features as a documented stand-in for the CNN, behind the same interface.
